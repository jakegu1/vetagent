### What held up
- **Every value that is not exactly `true` is refused.**
  - The values: `true` with a CR or LF after it, a tab or CR before or after it, a Cyrillic e
    (U+0435), full-width letters, a zero-width space inside or before it, a trailing NBSP, a

  - Look-alike names set to `true` are refused too: `github_actions`, `Github_Actions`,
    `GITHUB_ACTIONS_`, `_GITHUB_ACTIONS`, `GITHUB_ACTION`, `GITHUB_ACTIONS ` (with a trailing
    space) and `GH_ACTIONS`.
  - So is a call with 16 runner-like variables set and `GITHUB_ACTIONS` unset.
  - Every one of these exited 2, git never ran according to the trace, and the scratch repository
    was unchanged. The positive control in the same repository committed and printed "pushed on
    attempt 1".
- **Every way of invoking it is refused before git runs.** Tried: `sh`, `dash`, `bash --posix`,

  `env -i`, a real symlink, and running it by hand from a worktree of the scratch repository. The
  worktree run left the config every worktree shares unchanged.
- **Line endings.**
  - There is no `.gitattributes`. The index stores LF (`i/lf`), this checkout has CRLF because of
    the system-wide `core.autocrlf=true`, and CI checks out LF.
  - Git Bash strips CR whether the script comes from a file, stdin or a pipe, so the Windows run
    tests the same logic CI runs.
  - `dash` on a CRLF copy stops at `set: Illegal option -o pipefail` with exit 2, and no git runs.
  - Linux bash, where CR is an ordinary character in a word, was emulated by writing `chr(1)` in
    its place. At head the script exits 2 with no git command, both on and off Actions: the `if`
    never closes, so bash stops on a syntax error.
  - The base script under the same emulation wrote `vetagent-snapshot[bot]<CR>` into the config.
    So under WSL on this checkout, this change turns an identity rewrite into a refusal.

### Minor notes
1. **Four mutants survive** (the red-team's driver reproduces them):
   - **S4:** the "nothing new" branch without `exit 0`. The script falls through to an empty
     commit and a push that has nothing to send, and 164 checks still pass. Fix: in that test,
     also require that the trace shows no `push`.
   - **S5:** `[[ ... != [Tt]rue ]]` accepts `True`. The spec's AC 1 list, unlike T-006's, has no
     `True`; the shipped script does refuse it. Fix: add `("True", "GITHUB_ACTIONS=True")` to
     `SNAPSHOT_OFF_ACTIONS`.
   - **S6:** cutting the retry loop to two attempts survives, because nothing runs the path where
     every push fails. Fix: add a case where the scratch origin refuses every push, for example
     with `receive.maxInputSize=1` in its config. Assert exit 1, `LOST`, five attempts, and stub
     sleeps of 10 to 50 seconds.
   - **S13:** `date +%F` instead of `date -u +%F` survives whenever the local and UTC dates agree.
     On CI, which runs in UTC, it can never fail. Fix: give the calls on Actions a `TZ` whose date
     differs from UTC's at that moment.
2. **Linux is not measured.** The task branch is not on origin. The script's retry path is proven
   on Linux by the real bot runs, but the new harness steps (local clone, `push -u`, pull and
   rebase in the scratch repository, `BASH_ENV`) have only run on Windows. Pushing the branch
   would measure them before the merge, and that needs the Owner's yes.
3. **Nothing pins the scripts to LF.** A script committed with CRLF would stop the bot on Linux,
   both at head and at base, as the emulation shows. That risk predates this task, and the new
   checks would now turn `test.yml` red on the push that committed it. The fix is one
   `.gitattributes` line, `*.sh text eol=lf`, as a backlog item.
