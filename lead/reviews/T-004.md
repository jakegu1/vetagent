Head 92a818d. Nothing in the repository or the worktrees was changed. All work ran in scratch clones.

**What I tried:**
- 96 YAML shapes of `test.yml`, comparing the runner's reading with PyYAML (YAML 1.1) and with eemeli/yaml 2.8.3 (YAML 1.2, the library behind GitHub's own actions/languageservices parser).
- 36 `deploy.yml` mutants plus 4 multi-line ones, and 19 runner mutants, all run against `tests/test_deploy_gate.py`.
- The exit-status path from runner to wrapper to step to job.
- Removing `lead/` the way ADR-0001 describes.
- An LF checkout like CI's, and the guard under Python 3.11.
- CI timing and history, read-only through `gh run list/view`.
- GitHub's `if:` semantics, read from the actions/runner source.

**Not run:** Linux itself (WSL and Docker don't work on this machine) and GitHub's own YAML parser.

### What held up
- **YAML shapes.** None of these made the runner read fewer commands and pass: CRLF, CR, BOM, `---`/`%YAML`, tabs, quoted keys, `run :`, trailing spaces, comments after values, anchors/aliases/merge keys, flow `steps:` and flow steps, `- run:` as the first key, `|2 |1 |+ |- > >-`, compact and deep sequences, a bare `-`, comments at columns 0 and 2, a `run:` value on the next line, quoted values with operators or `\n` escapes, backslash continuation, duplicate keys. Each gives the same commands as the YAML parsers, a superset, or red / exit 2. On the real `test.yml` all three readers find 28 commands and nothing is unrecognised.
- **Exit status.** `runpy` passes `SystemExit` through the wrapper; the step is a single command under `bash -e`; later steps carry the implicit `success()`. No offline step reads `GITHUB_*` or opens a network connection.
- **`deploy.yml` mutants caught: 20 of 36**: gate moved after the deploy; `continue-on-error` (two forms, and on the job); `fetch-depth` removed or set to 1; gate `if: always()` or no `if`; deploy step with no `if`; `always() &&`, `!cancelled() &&`, `success() ||` on later steps; `|| true`, a block ending in `exit 0`, `shell:`; a second checkout; the gate running `lead/checks.py`, `python3`, or a quoted run.
- **Runner mutants caught: 15 of 19**, including "skip `- run:`" and "ignore unrecognised lines".
- **Runs:** LF checkout 28 of 28, exit 0, no tracked file modified. The guard passes 50 of 50 on Python 3.11. CI's `test` job on 16e100e took 32 s, well inside the deploy job's 20-minute timeout.

### Material findings
**M1. Removing `lead/` as ADR-0001 describes now blocks every deploy.**
- **Trigger:** ADR-0001's documented reversal ("delete `lead/` … Nothing else changed"). The spec's threat model names this cause: "removing `lead/` breaks or silently removes it".
- **Reproduction:** scratch clone at 92a818d, `git rm -r lead`, commit. `python tests/test_deploy_gate.py` prints `FAIL lead/checks.py is still there, for lead/config.yml and the lead kit  not found`: 44 passed, 1 failed, exit 1. `python .github/scripts/offline_suite.py` (the deploy's gate) prints `27 of 28 steps passed … RED The deploy runs every step of this job before it deploys`, exit 1, so nothing deploys. Control: at base a3c9db0 with `lead/` removed, the 27 steps pass, exit 0. The guard's wrapper check is the only offline step that needs `lead/`.
- **Impact:** the gate depends on the lead kit, which the threat model rules out. ADR-0001's reversibility claim becomes false.
- **Fix (one line, checked):** at the top of `test_the_wrapper_is_the_same_tool`, if `ROOT/lead` is not a directory, print "not checked here" and return. With that, the guard gives 44 passed and 0 failed without `lead/`, and 50 of 50 with it.

**M2. The guard reads `run:` and `if:` differently from GitHub, so a swallowed failure or an override passes it.**
- **What goes wrong:** the guard's `deploy.yml` reader keeps only the first line of a value continued on the next line. It reads a block scalar `if: >-` as the string `">-"`. It matches status functions case-sensitively.
- **Trigger:** softening the gate under the calendar-red pressure the spec describes, written wrapped the way this repo wraps lines longer than about 100 columns.
- **Reproduction:** add one line under the gate's run:
  ```
          run: python .github/scripts/offline_suite.py
            || true
  ```
  PyYAML and eemeli/yaml both read the run as `python .github/scripts/offline_suite.py || true`. The guard prints `PASS  it runs exactly … no || true …` and `50 passed, 0 failed`, exit 0.
- **Same result for:** `|| echo "::warning::…"` on the continuation line; `if: >-` on both steps with `!cancelled() &&` in the deploy's (YAML reads `!cancelled() && steps.creds.outputs.ready == 'true'`); a two-line plain `if:` adding `(success() || github.event_name == 'workflow_dispatch')`; `Always()`, `ALWAYS()`, `!Cancelled()`, `Failure()`. The actions/runner source compares status-function names case-insensitively (`ConvertToIfCondition` uses `OrdinalIgnoreCase`).
- **Impact:** criterion 4 ("no `|| true`, no `if:` that runs later steps after a failure") is enforced only for single-line, lowercase forms. The second amendment closed this exact shape in the runner but not in the guard's reader.
- **Fix (checked in scratch):** in the guard's `_step`, for keys other than `with`/`env`, keep all of a value's lines: a block scalar's lines joined, or a plain value plus its continuation lines. Add `re.I` to `STATUS_FUNCTIONS`. With that, all 4 multi-line and 4 case mutants are caught and the real tree stays 50 of 50.

### Minor notes
1. **Hidden line separators.** `str.splitlines()` also splits at `\x0b \x0c \x1c-\x1e \x85 U+2028 U+2029`. A comment containing one of these, followed by `  name:`, ends the job for the runner. Reproduced end to end: 1 of 2 steps run, "1 of 1 steps passed", exit 0. eemeli/yaml reads both steps; GitHub's parser is unverified. This needs a deliberately hidden character. One-line fix: refuse `test.yml` if it contains any of these characters.
2. **Quoted value wrapped at two spaces.** A quoted value continued at two-space indentation with `id:` (for example `name: 'b…` then `  x: y'`) ends the job early. PyYAML accepts it; YAML 1.2 rejects it. Contrived.
3. **Runner mutants the guard misses (4):** narrowing `SHELL_OPERATOR` to `&&|;` (which reopens `a.py | b.py`); ignoring the whole `|`/`&` family; silently dropping job-level lines after `steps:`; accepting anything under `with:`/`env:`. Fix: loop the chained case over every operator, and add one case for each of the other two.
4. **Accepted but ignored:** a `uses:` step other than checkout/setup-python is skipped, while the step's name says "every step"; `env:`, `working-directory:` and `shell:` on a step are not applied; `${{ }}`, quotes and `$VAR` arguments are passed literally. None of these is in use today. Fix: an allowlist for `uses:`, and refuse the rest.
5. **Of the 16 `deploy.yml` survivors:** 4 are M2's case forms and 1 is an equivalent rewrite (`- run:` first). 3 fail closed or are harmless: `working-directory`, a step timeout, an extra bench step. 8 need a deliberate edit: job- or workflow-level `defaults.run.shell` that swallows the exit status; `git checkout origin/master` after the gate; a `uses:` deploy action or `setup-uv` before the gate; `PYTHONINSPECT` (3 forms), believed not a bypass on CI's non-TTY stdin, not measured on Linux. Python-version skew between `test.yml` and `deploy.yml` is also unchecked.
6. **The gate runs its own guard.** A runner regression that returns 0 on red would pass inside the deploy, and only `tests`, which the deploy doesn't wait for, would show it.
7. **Manual dispatch.** `workflow_dispatch` can run `deploy.yml` from any branch, including branches cut before T-004. This predates the task.
8. **Next calendar red.** The first date-driven red that would block deploys is `test_gates_get_reviewed.py`'s 2026-10-16 gate, 17 days away.

**Threat model.** The gate must never pass having run fewer or different commands than GitHub
runs for `test.yml`'s `test` job; the guard must read `deploy.yml` the way GitHub does, or a

closed unrecognised lines. What is left of the class: values that span lines (quoted, flow,
folded, continued), characters Python splits lines on, step keys the runner accepts but does
not apply, and the guard's own reader of `deploy.yml`.

**Required**
1. **M1.** The guard's wrapper check says "not checked here" when `lead/` is absent, instead of
   failing. Test: in a scratch clone with `lead/` removed and committed,
   `python tests/test_deploy_gate.py` and `python .github/scripts/offline_suite.py` both exit
   0. Named change (d).
2. **M2.** The guard's `deploy.yml` reader keeps every line of a value (a block scalar's lines
   joined; a plain value with its continuation lines) and matches status functions without
   regard to case. Test: the eight M2 mutants (`|| true` and `|| echo` on a continuation line;
   `if: >-` with `!cancelled() &&`; a two-line plain `if:` with `success() ||`; `Always()`,
   `ALWAYS()`, `!Cancelled()`, `Failure()`) each turn the guard red; the real tree stays green.
   Named change (e).

   `steps:` in the `test` job, refuse (red, the line named): a value that opens a quote, `[` or

   any character `str.splitlines()` breaks on other than `\n` and `\r`. Named change (f): one
